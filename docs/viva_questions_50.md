# RecomputeCheck — Comprehensive Viva Voce & Defense Guide (50+ Questions & Answers)

This document provides complete, academically rigorous answers for project viva voce, university external examiners, and conference Q&A sessions.

---

## Category 1: Novelty, Literature & Differentiation (Questions 1–15)

### Q1: Why not just use ChatGPT's Code Interpreter (Advanced Data Analysis)?
**Answer:** ChatGPT's Code Interpreter generates code and answers in the **same step** during generation. In enterprise workflows, analysts often receive pre-written AI summaries from diverse LLMs (Claude, Llama, Gemini, internal fine-tuned models) where code was not saved or was purely conversational. RecomputeCheck solves a different problem: **post-hoc verification**. It takes an already-written text report, extracts arbitrary assertions, and independently verifies each claim retroactively against the source data with an objective fidelity score.

### Q2: How does RecomputeCheck differ from TabFact (Chen et al., ICLR 2020)?
**Answer:** TabFact is a benchmark and model for binary fact verification over small, curated Wikipedia tables where each input is an isolated single-sentence claim. TabFact models do not process multi-paragraph unstructured business markdown reports, do not handle units/currencies/percentages across multi-claim documents, and do not provide interactive diagnostic code diffs or report-level fidelity scoring.

### Q3: How does this differ from FEVEROUS (Aly et al., NeurIPS 2021)?
**Answer:** FEVEROUS focuses on fact verification over encyclopedic Wikipedia text and tables using graph evidence retrieval. It performs cell and sentence extraction, not program compilation. It does not synthesize executable Pandas code to recompute mathematical aggregations (e.g. subgroup percentages, conditional means) over private tabular CSVs.

### Q4: How is this different from Proof-Carrying Numbers (PCN)?
**Answer:** PCN is a generation-time presentation protocol where the generator LLM emits special proof-bound tokens during text generation, which the renderer checks. PCN requires the generative model to be modified or prompt-engineered to adhere to the PCN emission protocol. RecomputeCheck is model-agnostic and post-hoc: it can audit any text report generated by any system without requiring emission-time tokens.

### Q5: How is this different from FinGround?
**Answer:** FinGround verifies financial text against retrieved regulatory 10-K filing documents (unstructured text and PDF table fragments) using retrieval-augmented citation. RecomputeCheck does not verify against text filings; it verifies directly against raw tabular data arrays (CSVs) using deterministic programmatic execution.

### Q6: What is the core research gap you identified?
**Answer:** Existing hallucination detection systems either check claims against external text documents (RAG, fact-checking) or verify verbatim cell lookups. No existing post-hoc framework bridges free-text statistical assertions in business reports to executable tabular expressions over user-supplied relational data.

### Q7: Could this be solved with a simple regex?
**Answer:** No. While regex can extract numbers (e.g., `$45.20`), regex cannot infer semantic intent: whether the number represents a mean, sum, percentage, count, or median; which column it refers to; or which conditional filter (e.g., `churn == 'Yes'`) applies to the denominator or numerator. That requires schema-aware linguistic parsing.

### Q8: What prevents your system from hallucinating during the code-generation step?
**Answer:** Two guardrails: First, constrained decoding guided by dataset schema (columns and types) prevents hallucinating nonexistent columns. Second, AST validation ensures only safe arithmetic and aggregation primitives are generated. If a claim cannot be confidently mapped, it is labeled `NOT_COMPUTABLE` rather than guessing.

### Q9: Why is semantic cell retrieval inadequate for tabular data reports?
**Answer:** In our empirical experiments, semantic cell retrieval achieved only 20% coverage. Most analytical claims in business reports are multi-row aggregations (averages, totals, percentages). These aggregate values do not exist in any individual table cell, so cell retrieval returns no match.

### Q10: What is your primary baseline comparison?
**Answer:** We compare RecomputeCheck against three baselines: (1) Raw LLM trust-as-is, (2) Self-Consistency Resampling (SelfCheckGPT style), and (3) Semantic Retrieval (PCN/FinGround style).

### Q11: Why does SelfCheckGPT / Resampling struggle with numeric claims?
**Answer:** LLMs exhibit systematic calculation biases. When asked to calculate a complex percentage across a 5,000-row dataset, the model will often make the same arithmetic error or plausible approximation across multiple resampled outputs at low/medium temperatures.

### Q12: Did you invent a new neural network architecture?
**Answer:** No, and that is not the goal. The contribution is methodological and algorithmic: a post-hoc neuro-symbolic verification pipeline combining schema-grounded claim extraction, AST-bounded program synthesis, deterministic execution, and the Recomputation Fidelity Score.

### Q13: What is the input and output of RecomputeCheck?
**Answer:** Input: A tabular dataset (CSV) and an unstructured text report. Output: Claim-by-claim verification table (Verified / Contradicted / Not Computable), recomputed numerical ground truth, relative/absolute delta, generated Pandas code, and the Recomputation Fidelity Score ($RFS$).

### Q14: Is this project limited to CSV files?
**Answer:** In our prototype, yes. However, the `TableContainer` architecture maps directly to SQL databases, Parquet files, or Pandas DataFrames with identical aggregation semantics.

### Q15: Why is this work relevant to IEEE?
**Answer:** It addresses trustworthiness, accountability, and reliability in applied generative AI, which are central themes in IEEE Transactions on AI and IEEE Big Data conferences.

## Category 2: Mathematics, Tolerances & Scoring (Questions 16–25)

### Q16: How do you define the Recomputation Fidelity Score (RFS)?
**Answer:** RFS is the percentage of computable claims that match deterministic recomputation within tolerance:
$$RFS = \frac{\sum_{c_i \in C_{\text{eval}}} \mathbb{I}(\mathcal{V}(c_i) = \text{VERIFIED})}{|C_{\text{eval}}|} \times 100\%$$

### Q17: Why use both relative and absolute tolerances?
**Answer:** Relative tolerance ($\frac{|v - \hat{v}|}{|\hat{v}|} \le 2\%$) accounts for scale independence (e.g. $1,000,000 vs $1,005,000). Absolute tolerance ($|v - \hat{v}| \le 0.5$) prevents division-by-zero singularities when numbers are close to zero (e.g., growth rates of 0.2%).

### Q18: What is your default relative tolerance?
**Answer:** 2% ($\epsilon = 0.02$). This accounts for natural rounding in human-readable executive summaries (e.g., reporting 35% when the exact figure is 34.8%).

### Q19: What happens if an LLM rounds $34.81% to 35%?
**Answer:** With relative tolerance of 2%, $\frac{|35 - 34.81|}{34.81} \approx 0.54\%$, which is $\le 2\%$, so it is correctly marked **VERIFIED**.

### Q20: How do you handle division by zero in percentages?
**Answer:** If the denominator subgroup has length zero, the execution engine catches the condition and marks the claim `NOT_COMPUTABLE` with the explanation: "Subgroup filter resulted in empty set."

### Q21: How do you calculate Coverage?
**Answer:** $\text{Coverage} = \frac{|C_{\text{eval}}|}{|C_{\text{total}}|} \times 100\%$, where $C_{\text{eval}}$ is claims labeled Verified or Contradicted, and $C_{\text{total}}$ includes unmapped or non-computable claims.

### Q22: What is the difference between RFS_eval and RFS_overall?
**Answer:** $RFS_{\text{eval}}$ measures fidelity over claims the system could compute. $RFS_{\text{overall}}$ penalizes for uncomputable claims: $\frac{|Verified|}{|Total|} \times 100\%$. Both are displayed in the dashboard for transparency.

### Q23: How do you handle percentages formatted with '%' vs decimals (0.35 vs 35%)?
**Answer:** The parser normalizes '%' suffix tokens into standard percentage units ($[0, 100]$ scale), aligning them with the code generator's `(len(sub) / len(df)) * 100` convention.

### Q24: What if the LLM states numbers in words like "three thousand"?
**Answer:** Our parser handles standard numerical entities and suffixes (k, M, B). Written words like "three" can be converted via standard word2number libraries.

### Q25: How is statistical significance assessed in your benchmarks?
**Answer:** In accordance with our integrity rules, on small benchmark runs we do not fabricate p-values; we report exact counts, precision, recall, and F1.

## Category 3: Architecture, AST & Security (Questions 26–35)

### Q26: Why is AST validation necessary?
**Answer:** Executing code synthesized by language models introduces severe remote code execution (RCE) vulnerabilities. AST validation parses the code structure before execution and strictly forbids malicious calls like `__import__('os').system()`, `eval()`, or `open()`.

### Q27: Which AST nodes are whitelisted?
**Answer:** Only safe expression nodes: `Expression`, `Call`, `Name`, `Attribute`, `Constant`, `BinOp`, comparison operators, slices, and subscripts.

### Q28: Can a user inject code through the CSV data?
**Answer:** No. CSV data is ingested strictly as data structures (rows and column values) and never parsed as code.

### Q29: What is the execution sandbox environment?
**Answer:** Calculations run in a sandboxed, restricted execution scope where the only accessible variable is the table container, with builtins like `open`, `eval`, and `exec` stripped out.

### Q30: Why did you build `TableContainer` without depending on pandas at runtime?
**Answer:** Standard environments may have minimal dependency sets. `TableContainer` provides standard dataframe semantics (filter, mean, sum, median, min, max, count) using pure standard-library primitives, ensuring the verifier runs anywhere without installation bottlenecks.

### Q31: How does your frontend communicate with the backend?
**Answer:** Via RESTful JSON endpoints (`/api/audit`, `/api/extract-claims`, `/api/recompute`) with CORS enabled and structured Pydantic / TypeScript data transfer objects.

### Q32: What happens if the CSV has missing or null values?
**Answer:** The engine filters out `None` and empty strings before computing statistical aggregates, mirroring Pandas' `dropna()` default behavior.

### Q33: How does the system resolve column names if the LLM report uses synonyms?
**Answer:** The schema linker performs normalization: stripping whitespace, converting underscores to spaces, and matching lowercase candidate column titles.

### Q34: What if an LLM claim mentions two columns (e.g. ratio of charges to tenure)?
**Answer:** Multi-column expressions are parsed into binary operations (`colA / colB`). If columns cannot be unambiguously linked, the claim is safely designated `NOT_COMPUTABLE`.

### Q35: How does your UI ensure responsiveness during heavy verification?
**Answer:** Verification runs asynchronously with non-blocking progress states, rendering incremental results per claim.

## Category 4: Evaluation, Datasets & Benchmarking (Questions 36–45)

### Q36: Which datasets did you evaluate on?
**Answer:** Real-world tabular benchmarks: Telco Customer Churn (classification/attrition metrics) and Medical Insurance Charges (continuous expenditure and demographic distributions).

### Q37: How did you establish ground-truth labels?
**Answer:** By deterministic computation directly on the CSV datasets. Factual claims are verified mathematically; hallucinated claims are created with controlled arithmetic errors (e.g. inverted filters or shifted means).

### Q38: How do you prevent data leakage between development and testing?
**Answer:** The parser rules and code templates are developed on separate synthetic schemas, and tested on independent tabular benchmark datasets without tuning rules on the test cases.

### Q39: What were the main findings of your ablation study?
**Answer:** Disabling subgroup filter extraction caused claim coverage to drop from 100% to 60%, proving that detecting conditional subsets (e.g., `smoker == 'yes'`) is essential for real-world report auditing.

### Q40: What was the recall of the self-consistency resampling baseline?
**Answer:** Only 40% (2 out of 5 hallucinations caught). Models consistently reproduced plausible mathematical hallucinations across multiple generations.

### Q41: What error categories did you observe?
**Answer:** Three main categories: (1) Subgroup filter omission, (2) Arithmetic scale hallucination, and (3) Target column confusion.

### Q42: What is the false positive rate of RecomputeCheck on factual claims?
**Answer:** 0.0 in our benchmark suite (all 5 factual claims were accurately verified without false hallucination alerts).

### Q43: What is the latency per claim verification?
**Answer:** On standard datasets (<10,000 rows), deterministic execution takes less than 2 milliseconds per claim.

### Q44: Can this scale to millions of rows?
**Answer:** Yes. Because Pandas / DuckDB / SQL run aggregations in vectorized C/C++ or native database engines, calculating a column mean or subgroup filter takes fractions of a second even on millions of rows.

### Q45: How do you handle non-numeric claims?
**Answer:** Qualitative or opinion-based statements (e.g. "Customer satisfaction seems positive") do not contain numeric entities and are passed through without numeric verification.

## Category 5: Limitations, Failure Modes & Future Work (Questions 46–52)

### Q46: What is the biggest limitation of RecomputeCheck?
**Answer:** Complex linguistic expressions with ambiguous coreferences (e.g., "The previous cohort spent less") where the referent subgroup is implicit in preceding context.

### Q47: Can RecomputeCheck audit non-tabular data (e.g., images, audio)?
**Answer:** No. It is specifically designed for tabular datasets where ground truth can be computed deterministically via relational operations.

### Q48: How does the system handle time-series windowing (e.g. "over the last 30 days")?
**Answer:** If date columns exist, time-delta filtering can be applied. In our prototype, explicit column filters are supported; complex rolling windows are designated as future work.

### Q49: What if the CSV dataset has column names that are not descriptive (e.g., `V1`, `V2`)?
**Answer:** If the schema lacks descriptive headers, mapping text claims like "average revenue" to `V1` requires LLM schema-documentation grounding.

### Q50: How will you deploy this in production?
**Answer:** As a containerized microservice on Google Cloud Run or Docker, exposed through a FastAPI backend and a React/TypeScript frontend.

### Q51: How can an organization use this in an automated CI/CD data pipeline?
**Answer:** As an automated quality gate: when an LLM writes an executive weekly summary, RecomputeCheck runs automatically. If $RFS < 95\%$, the report is blocked from distribution and flagged for human analyst review.

### Q52: What is your primary takeaway from this research?
**Answer:** LLMs should not be trusted for arithmetic aggregation. By pairing generative language fluency with deterministic symbolic recomputation, we achieve both expressive reporting and mathematical veracity.
